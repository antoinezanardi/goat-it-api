# ARCH — Architecture & design

Conformance of the repository to its canonical architecture guide, `docs/architecture.md`: the hexagonal layering of this NestJS 12 + Fastify 5 + Mongoose 9 API (`src/contexts/<context>/{domain,application,infrastructure,contracts}`, the layered `src/shared` kernel, `src/app` as application shell, `src/infrastructure` as the cross-cutting adapter area), the dependency direction that keeps domain and application framework-free, the per-layer cross-context published surface, module wiring through persistence and usage modules, path aliases, DTO and error placement, and the test/package layout. A check here fails when a file sits in the wrong area, a dependency points the wrong way, a companion is missing, or an architectural exception was invented instead of recorded.

**Decision doc:** `docs/architecture.md` (section `## GOAT audit decisions`). **Diff triggers:** see SKILL.md category index.

**Not in this category:** framework API correctness (NestJS DI runtime, Fastify adapter behaviour, Mongoose options, Zod/nestjs-zod usage, SWC/ESM build mechanics) → STACK · TypeScript strictness, naming, exports, magic values, lint health and error-handling style → CODE · test strategy, coverage, mutation and acceptance execution → TEST · actual MongoDB schemas, indexes and query shapes → DATA · container, environment and runtime platform → PLAT · secrets, authentication and input-hardening consequences → SEC · timeout, retry and failure-mode behaviour → REL

## 1. Layering and dependency direction

- **[ARCH-01] Domain stays pure, deterministic and framework-free** — Every module under a context `domain/` imports only its own domain, another context's published domain types/constants/rules/errors, `@shared/domain`, `@shared/types` and type-only `type-fest`; it imports no `@nestjs/*`, `mongoose`, `fastify`, `nestjs-zod`, `zod`, `node:*`, no application or infrastructure code, and performs no `fs`, `crypto`, `process.cwd()`, clock, network or environment access.
  Evidence: `static` · Diff: ✓ · Core: ✓ · Severity: high · Look: `src/contexts/*/domain/**`, `src/shared/domain/**` · Src: [6], project: docs/architecture.md §3.3, project: docs/architecture.md §3.4, project: docs/architecture.md §4.1, project: docs/architecture.md §12.2
- **[ARCH-02] Application depends inward and imports no framework** — Every module under `application/` imports own domain/application/contracts, another context's published use cases and published surface, `@shared/domain`, `@shared/application`, `@shared/types`, `zod` and type-only `type-fest`; it imports no infrastructure, no `@nestjs/*`, `mongoose`, `fastify` or `nestjs-zod`.
  Evidence: `static` · Diff: ✓ · Core: ✓ · Severity: high · Look: `src/contexts/*/application/**`, `src/shared/application/**` · Src: project: docs/architecture.md §3.3, project: docs/architecture.md §4.2, project: docs/architecture.md §12.2
- **[ARCH-03] Infrastructure depends inward and never sideways across contexts** — A context's `infrastructure/` imports its own domain/application/infrastructure/contracts, another context's published contracts and published domain types, all shared layers, framework packages and `@src/infrastructure/*`; it never imports another context's application use cases, internal mappers, internal DTOs or Mongoose schemas, and never imports `@app/*`.
  Evidence: `static` · Diff: ✓ · Core: ✓ · Severity: high · Look: `src/contexts/*/infrastructure/**` · Src: project: docs/architecture.md §3.2, project: docs/architecture.md §4.3
- **[ARCH-04] Contracts remain a pure facade** — A `contracts/` folder imports only its own domain, `@shared/domain`, pure `@shared/application`, `zod` and type-only `type-fest`; it never imports its own or another context's application/infrastructure, `@shared/infrastructure`, Mongoose, NestJS, Fastify or `nestjs-zod`.
  Evidence: `static` · Diff: ✓ · Severity: high · Look: `src/contexts/*/contracts/**` · Src: project: docs/architecture.md §3.2, project: docs/architecture.md §4.4, project: docs/architecture.md §12.1
- **[ARCH-05] Shared kernel stays context-free and one-way** — `src/shared` imports no bounded context and no `src/app`; `shared/domain` imports neither `shared/application` nor `shared/infrastructure`, and `shared/application` imports no `shared/infrastructure`, with only the single localization `AppConfigService` exception recorded in §13 of the guide.
  Evidence: `static` · Diff: ✓ · Core: ✓ · Severity: high · Look: `src/shared/**` · Src: [6], project: docs/architecture.md §3.3, project: docs/architecture.md §4.5, project: docs/architecture.md §13
- **[ARCH-06] Cross-cutting infrastructure stays context-free** — Modules under `src/infrastructure/` import only shared layers, framework packages and their own subtree; they import no bounded context and no `src/app`, and `server.ts` receives the application module as a `Type<unknown>` parameter instead of importing `AppModule`.
  Evidence: `static` · Diff: ✓ · Severity: high · Look: `src/infrastructure/**`, `src/infrastructure/api/server/server.ts` · Src: project: docs/architecture.md §3.1, project: docs/architecture.md §4.6, project: docs/architecture.md §6.1
- **[ARCH-07] Application shell composes but owns no business logic** — `src/app/` contains only the root controller, app-metadata DTO, logger helpers, shell service, `app.module.ts` and the global HTTP exception filter; business rules, repository access and domain decisions live in the owning context, and no context imports `@app/*`.
  Evidence: `static` · Diff: ✓ · Severity: medium · Look: `src/app/**` · Src: project: docs/architecture.md §2.1, project: docs/architecture.md §4.6
- **[ARCH-08] The module and import graph is acyclic** — Imports create no runtime cycle between contexts, shared layers, the app shell and infrastructure; `import-x/no-cycle` stays enabled, no `forwardRef` is introduced, and a cycle is resolved by extracting persistence wiring or revisiting the boundary instead of adding a reference.
  Evidence: `static` · Diff: ✓ · Severity: high · Look: `src/contexts/**`, `src/shared/**`, `src/app/**` · Src: [7], project: docs/architecture.md §6.2, project: docs/architecture.md §12.3

## 2. File placement and naming

- **[ARCH-09] Placement follows the decision tree** — Every added or moved file applies the §2.2 order (entrypoint → business behaviour → published contract → cross-cutting infrastructure → shared kernel → app shell → test → tooling) and lands under the owning area: `src/contexts/<context>/{domain,application,infrastructure,contracts}`, `src/shared/{domain,application,infrastructure,types}`, `src/app`, `src/infrastructure`, `packages/schemas/`, `public/`, `tests/`, `configs/`, `scripts/`, `docs/`, `env/`, `docker/`, `.github/`, `.opencode/` or `.agents/`; no new top-level folder and no `misc` bucket appears, and context or domain directory names are singular (`question-theme/`, not `question-themes/`).
  Evidence: `static` · Diff: ✓ · Core: ✓ · Severity: medium · Look: `src/contexts/**`, `src/shared/**`, `src/app/**`, `src/infrastructure/**` · Src: project: docs/architecture.md §2.1, project: docs/architecture.md §2.2, project: docs/architecture.md §8.3
- **[ARCH-10] One artifact family per folder, no loose kinds** — A folder holds one artifact family; constants, types, helpers, mappers, errors, rules, schemas and pipelines sit in their kind subfolder (`constants/`, `types/`, `helpers/`, `mappers/`, `errors/`, `rules/`, `schemas/`, `pipelines/`), no loose constants/types/helpers sit beside a class file, no empty kind folder is created, and a purely local type is colocated as `<source-basename>.types.ts`.
  Evidence: `static` · Diff: ✓ · Severity: medium · Look: `src/contexts/**`, `src/shared/**`, `src/app/**` · Src: [8], project: docs/architecture.md §4.2, project: docs/architecture.md §8.2

## 3. Module wiring

- **[ARCH-19] The persistence module owns schema, adapter and token** — `<context>-persistence.module.ts` registers the schema through `MongooseModule.forFeature`, provides the domain repository token with the Mongoose adapter and exports that token; feature modules never register schemas directly.
  Evidence: `static` · Diff: ✓ · Core: ✓ · Severity: high · Look: `src/contexts/*/infrastructure/persistence/*-persistence.module.ts` · Src: [1], [2], project: docs/architecture.md §6.2, project: docs/architecture.md §6.4
- **[ARCH-20] The context module wires controllers and use cases only** — `<context>.module.ts` imports its persistence module and any consumer module, registers its controllers and use cases, and exports only the providers another context consumes; it does not export its whole provider set.
  Evidence: `static` · Diff: ✓ · Severity: high · Look: `src/contexts/*/*.module.ts` · Src: [1], project: docs/architecture.md §6.2
- **[ARCH-21] The usage module exposes exactly one published reverse dependency** — `<context>-usage.module.ts` imports the persistence module, provides the published use case and exports it; the consuming context imports the usage module rather than the provider's feature module.
  Evidence: `static` · Diff: ✓ · Severity: high · Look: `src/contexts/*/*-usage.module.ts` · Src: project: docs/architecture.md §5.2, project: docs/architecture.md §6.2
- **[ARCH-22] Plain use cases are wired through `createUseCaseProvider`** — A use case appears in `providers` only through `createUseCaseProvider(UseCase, [tokens])`, its token array matches the constructor parameter order, the class is not also listed bare, and `@Inject()` is not mixed with the `inject` array.
  Evidence: `static` · Diff: ✓ · Severity: high · Look: `src/contexts/*/*.module.ts`, `src/shared/infrastructure/nest/helpers/**` · Src: [2], project: docs/architecture.md §6.3
- **[ARCH-23] No context re-registers another context's schema, repository or token** — Consumers import the owning module or usage module; no module repeats `MongooseModule.forFeature` for another context's schema, provides another context's repository token or declares another context's exported class; every class token injected across a module boundary is exported by the owning module.
  Evidence: `static` · Diff: ✓ · Severity: high · Look: `src/contexts/*/*.module.ts`, `src/contexts/*/infrastructure/persistence/*-persistence.module.ts` · Src: [1], project: docs/architecture.md §6.2, project: docs/architecture.md §6.3
- **[ARCH-24] The module graph avoids `forwardRef` and factory cycles** — No `forwardRef` is used to hide a boundary problem, no two factory providers depend on each other, and a cycle is resolved by extracting the persistence wiring or revisiting the context boundary.
  Evidence: `static` · Diff: ✓ · Severity: medium · Look: `src/contexts/**`, `src/app/**` · Src: [1], project: docs/architecture.md §6.2, project: docs/architecture.md §6.3

## 4. Cross-context published surface

- **[ARCH-25] The published surface is demand-driven and registered** — A context publishes only use cases, domain types/constants/rules/errors and `contracts/` that another context actually consumes; every new published item updates the §5.2 register and the per-layer lint allowlist in the same change, and no speculative export is added.
  Evidence: `static` · Diff: ✓ · Severity: medium · Look: `src/contexts/*/contracts/**`, `src/contexts/*/application/use-cases/**` · Src: project: docs/architecture.md §5.1, project: docs/architecture.md §5.2, project: docs/architecture.md §12.3
- **[ARCH-26] Cross-context imports stop at the published surface** — A consumer imports only the provider's published use cases, published domain types/constants/pure rules/errors and `contracts/`; it never imports the provider's infrastructure, internal mappers, internal DTOs, Mongoose schemas or non-published application code, and the per-layer allowlist is narrower than a context-wide grant.
  Evidence: `static` · Diff: ✓ · Core: ✓ · Severity: high · Look: `src/contexts/*/domain/**`, `src/contexts/*/application/**`, `src/contexts/*/infrastructure/**` · Src: [6], project: docs/architecture.md §3.2, project: docs/architecture.md §5.1, project: docs/architecture.md §12.1
- **[ARCH-27] Published use cases exchange only published types** — A published use case accepts and returns primitives, published domain types or published contract types; it never exposes an application command or an internal type, and the use case class remains the stable token whose public method signature is the consumer contract.
  Evidence: `static` · Diff: ✓ · Severity: medium · Look: `src/contexts/*/application/use-cases/**` · Src: project: docs/architecture.md §5.1
- **[ARCH-28] Published domain types are read-only snapshots** — A consumer never mutates or persists another context's entity, and when it needs only a subset it defines a local read model and maps the published type into it instead of importing the full entity by default.
  Evidence: `static` · Diff: ✓ · Severity: medium · Look: `src/contexts/*/domain/**`, `src/contexts/*/application/**`, `src/contexts/*/infrastructure/**` · Src: project: docs/architecture.md §3.2, project: docs/architecture.md §5.1
- **[ARCH-29] Cross-context persistence uses published persistence contracts** — A cross-context join or read uses collection names, field names and status values from `contracts/persistence/<concept>.persistence.contracts.constants.ts` and structural shapes from `<concept>.persistence.contracts.types.ts`; it never hardcodes a collection name, field path or status literal, and it never imports the provider's schema or Mongoose mapper.
  Evidence: `static` · Diff: ✓ · Severity: high · Look: `src/contexts/*/contracts/persistence/**`, `src/contexts/*/infrastructure/persistence/**` · Src: project: docs/architecture.md §5.4
- **[ARCH-30] Errors are consumer-owned unless explicitly published** — A consumer defines its own rule errors in its `domain/errors/` and never throws an unpublished provider error; only errors listed as published (for example the theme-not-found error) cross the context boundary.
  Evidence: `static` · Diff: ✓ · Severity: medium · Look: `src/contexts/*/domain/errors/**` · Src: project: docs/architecture.md §5.3

## 5. Path aliases and imports

- **[ARCH-31] Source and test imports use aliases, never relative paths** — Files under `src/`, `tests/` and `packages/schemas/src/` import through the registered aliases (`@src/*`, `@app/*`, `@shared/*`, `@question/*`, `@question-theme/*`, `@unit-tests/*`, `@mocks/*`, `@faketories/*`, `@test-helpers/*`, `@acceptance-*/*`); no `./` or `../` specifier appears, while `configs/` and `scripts/` may use relative imports.
  Evidence: `static` · Diff: ✓ · Core: ✓ · Severity: high · Look: `src/**`, `tests/**`, `packages/schemas/src/**` · Src: [6], project: docs/architecture.md §9, project: docs/architecture.md §12
- **[ARCH-32] Alias registries agree across SWC, TypeScript and Vitest** — Every production alias resolves in `configs/swc/swc.config.json` and `configs/typescript/tsconfig.app.json`; every alias used by the Vitest unit suite resolves in `configs/typescript/tsconfig.spec.json` and `configs/vitest/vitest.config.ts`; every acceptance alias resolves in `configs/typescript/tsconfig.acceptance.json`; and a new bounded context registers its `@<context>/*` alias in the SWC, TypeScript and Vitest configurations in the same change.
  Evidence: `static` · Diff: ✓ · Severity: high · Look: `configs/swc/swc.config.json`, `configs/typescript/tsconfig.app.json`, `configs/typescript/tsconfig.spec.json`, `configs/typescript/tsconfig.acceptance.json`, `configs/vitest/vitest.config.ts` · Src: [10], project: docs/architecture.md §9, project: docs/architecture.md §9.1, project: AGENTS.md
- **[ARCH-33] The alias vocabulary stays minimal** — No alias is added for an existing area just for readability; `@src/*` remains the cross-cutting alias, dedicated aliases exist only for bounded contexts and the documented test areas, and a new alias is introduced only through an approved design.

- **[ARCH-34] No default exports, barrels or re-export-only files** — Production files use named exports; no default export, barrel file or file that only re-exports another module exists, except the `packages/schemas` entrypoint `index.ts` files and the config files whose tooling requires a default export.

## 6. Error placement and classification

- **[ARCH-36] Domain errors carry identity and structured context** — A domain error is a class extending `Error`, sets `this.name` in its constructor, carries the structured context the HTTP mapping needs and has a colocated spec; it does not depend on NestJS, Fastify or HTTP status codes.
  Evidence: `static` · Diff: ✓ · Severity: medium · Look: `src/contexts/*/domain/errors/**` · Src: [3], project: docs/architecture.md §7.4, project: docs/architecture.md §8.1
- **[ARCH-37] `GlobalExceptionFilter` is the single cross-context composition point** — The filter lives at `src/app/filters/global-exception/global-exception.filter.ts`, is registered with `APP_FILTER` in `AppModule`, owns the domain-error-to-HTTP mapping, and no context, shared middleware or infrastructure adapter duplicates that mapping.
  Evidence: `static` · Diff: ✓ · Severity: high · Look: `src/app/filters/global-exception/**`, `src/app/app.module.ts` · Src: [3], project: docs/architecture.md §4.6, project: docs/architecture.md §7.4
- **[ARCH-38] Only client-actionable errors map to 4xx** — A domain error maps to a specific HTTP status only when the client can act on it (validation, not found, conflict, forbidden); unexpected, invariant-violation and persistence-write failures fall through to 500, and every new domain error is classified in the PR as mapped or intentionally 500 with a one-line justification.
  Evidence: `static` · Diff: ✓ · Severity: high · Look: `src/app/filters/global-exception/**`, `src/contexts/*/domain/errors/**` · Src: project: docs/architecture.md §7.4, project: AGENTS.md
- **[ARCH-39] The four write/read-back errors stay intentionally 500 and test-locked** — `QuestionCreationError`, `QuestionThemeAssignmentCreationError`, `QuestionThemeAssignmentModificationError` and `QuestionThemeAssignmentRemovalError` are absent from the mapping table and the filter spec asserts their 500 behaviour, so the intent cannot silently drift.
  Evidence: `static` · Diff: ✓ · Severity: medium · Look: `src/app/filters/global-exception/**`, `src/contexts/question/domain/errors/**` · Src: project: docs/architecture.md §7.4
