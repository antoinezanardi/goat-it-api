# Internationalization

This document records the internationalization (i18n) design of the Goat It API (`goat-it-api`): the `Accept-Language` handling pipeline, the supported locales, fallback behavior, how localized question and question-theme content is stored per locale, the translation-completeness validation rules, the applicable-locales policy and the `translate-questions` maintenance command. It is based on the localization middleware and decorators (`file:src/shared/infrastructure/http/middlewares/localization/localization.middleware.ts`, `file:src/shared/infrastructure/http/decorators/localization/localization.decorator.ts`), the locale value object (`file:src/shared/domain/value-objects/locale/`), the localization Zod validators and mappers (`file:src/shared/application/`), the translation-completeness helpers (`file:src/shared/infrastructure/persistence/mongoose/helpers/translation-completeness.mongoose.helpers.ts`) and the maintenance command (`file:.opencode/commands/translate-questions.md`). Every claim cites the repository file it is based on.

## Supported locales and configuration

Six locales are supported: `en`, `fr`, `es`, `de`, `it`, `pt` — `LOCALES` in `file:src/shared/domain/value-objects/locale/locale.constants.ts`, typed as `Locale` in `file:src/shared/domain/value-objects/locale/locale.types.ts`.

The fallback locale is configured through the `FALLBACK_LOCALE` environment variable, validated by `z.enum(LOCALES)` with `DEFAULT_ENV_FALLBACK_LOCALE = "en"` as default (`file:src/infrastructure/api/config/schemas/env.schema.ts`, `file:src/infrastructure/api/config/constants/env.constants.ts`; `env/.env.example` and `env/.env.test` both set `FALLBACK_LOCALE=en`). It is exposed by `AppConfigService.localizationConfig` (`file:src/infrastructure/api/config/providers/services/app-config.service.ts`).

## Accept-Language handling pipeline

`LocalizationMiddleware` (`file:src/shared/infrastructure/http/middlewares/localization/localization.middleware.ts`) is applied to all routes (`consumer.apply(LocalizationMiddleware).forRoutes("*")` in `file:src/app/app.module.ts`) and resolves one `LocalizationOptions { locale, fallbackLocale }` per request:

- Only the **first locale** of the `Accept-Language` header is considered: the header is trimmed, the first 2 characters are lowercased (`getFirstLocaleFromHeader`, same file).
- `*` (wildcard) resolves to the configured fallback locale.
- No header → the configured fallback locale is used for both `locale` and `fallbackLocale`.
- An unrecognized value throws `400 Bad Request` listing the supported locales (same file).
- The resolved options are attached to `request.raw.localizationOptions` (`file:src/shared/infrastructure/http/types/fastify/fastify.types.ts`).

Controllers read them with the `@Localization()` parameter decorator, which throws `InternalServerErrorException` if the middleware did not run (`file:src/shared/infrastructure/http/decorators/localization/localization.decorator.ts`). Game-facing controllers use it: question list/random/by-id (`file:src/contexts/question/infrastructure/http/controllers/question/question.controller.ts`) and theme list/by-id (`file:src/contexts/question-theme/infrastructure/http/controllers/question-theme/question-theme.controller.ts`).

### Fallback behavior at response time

`pickLocalizedValue` returns `localizedValue[locale] ?? localizedValue[fallbackLocale]`; `createTranslationFromLocalizedText` / `createTranslationsFromLocalizedTexts` then emit the warning string `⚠️ No Translation found for desired locale (…) and fallback locale (…)` when both are missing (`file:src/shared/application/mappers/localization/localization.mappers.ts`). Question DTO mapping localizes statement/answer/context/trivia with these helpers (`file:src/contexts/question/application/mappers/question.mappers.ts`), theme DTO mapping localizes label/aliases/description (`file:src/contexts/question-theme/contracts/dto/question-theme.dto.mappers.ts`).

### Localization scope of endpoints

Game-facing question and theme endpoints localize their response text per request locale (`file:src/contexts/question/infrastructure/http/controllers/question/question.controller.ts`, `file:src/contexts/question-theme/infrastructure/http/controllers/question-theme/question-theme.controller.ts`). Admin endpoints do not localize: they return the full partial per-locale objects so the content can be edited — `createAdminQuestionDtoFromEntity` returns `question.content` and `applicableLocales` as stored (`file:src/contexts/question/application/mappers/question.mappers.ts`), and the admin question-theme DTO mapper returns the raw localized fields (`file:src/contexts/question-theme/contracts/dto/question-theme.dto.mappers.ts`).

### Accept-Language parsing examples

`getFirstLocaleFromHeader` takes the first 2 characters, lowercased — region subtags and q-values are ignored by design (`file:src/shared/infrastructure/http/middlewares/localization/localization.middleware.ts`):

| Header value | Result |
|---|---|
| `fr-FR, fr;q=0.9` | `fr` |
| `En` | `en` |
| `*` | configured fallback locale |
| `de-DE` | `de` |
| absent | fallback locale for both `locale` and `fallbackLocale` |
| `xyz` | `400 Bad Request` listing the supported locales |

### Locale labels and examples

Swagger examples are defined per locale: `LOCALE_LABELS` maps `en: English`, `fr: French`, `es: Spanish`, `de: German`, `it: Italian`, `pt: Portuguese`; `LOCALE_EXAMPLES` holds a sample string per locale (`file:src/shared/domain/value-objects/locale/locale.constants.ts`, `file:src/shared/application/dto/zod/validators/localization/constants/localization.zod.validators.constants.ts`). The shared `isValidLocale` guard implements the same membership check as the middleware (`file:src/shared/domain/value-objects/locale/helpers/locale.helpers.ts`).

## Per-locale content storage

Localized values are stored as partial per-locale objects — one optional field per locale key, `undefined` (absent) when untranslated. Persistence schemas: `LocalizedTextMongooseSchema` (six optional string props `en..pt`, `file:src/shared/infrastructure/persistence/mongoose/schemas/localization/localized-text.mongoose.schema.ts`) and `LocalizedTextsMongooseSchema` (six optional string-array props, `file:src/shared/infrastructure/persistence/mongoose/schemas/localization/localized-texts.mongoose.schema.ts`); domain types `LocalizedText = Record<Locale, string>` / `LocalizedTexts = Record<Locale, string[]>` and their `Partial` variants (`file:src/shared/domain/value-objects/locale/locale.types.ts`).

- Question content: `content.statement` (mandatory), `content.answer` (mandatory), `content.context` (optional), `content.trivia` (optional) — each a localized subdocument (`file:src/contexts/question/infrastructure/persistence/mongoose/schemas/question-content/question-content.mongoose.schema.ts`).
- Theme content: `label`, `aliases`, `description` — all mandatory localized subdocuments (`file:src/contexts/question-theme/infrastructure/persistence/mongoose/schemas/question-theme.mongoose.schema.ts`).
- Admin responses return the full partial per-locale objects (`createAdminQuestionDtoFromEntity` / `createAdminQuestionThemeDtoFromEntity`), while game responses return the single resolved string(s) per request locale (see above).
- Input validation: per-locale entries are trimmed strings of 1..500 chars, per-locale arrays of 1..10 items, and each `LocalizedText`/`LocalizedTexts` must contain at least one locale value (`file:src/shared/application/dto/zod/validators/localization/localization.zod.validators.ts` and its constants file).

## Translation-completeness rules

A resource is **fully translated** when every mandatory localized field has a value in every applicable locale, and every optional localized field is either absent (never translated) or has a value in every applicable locale — documented in the OpenAPI description of `zIsFullyTranslated` (`file:src/shared/application/dto/zod/validators/translation-completeness/translation-completeness.zod.validators.ts`).

Field specs (`TranslationCompletenessFieldSpec`): questions — `content.statement` and `content.answer` mandatory, `content.context` and `content.trivia` optional (`QUESTION_TRANSLATION_COMPLETENESS_FIELD_SPECS` in `file:src/contexts/question/infrastructure/persistence/mongoose/constants/question.mongoose.constants.ts`); themes — `label`, `aliases`, `description` all mandatory (`QUESTION_THEME_TRANSLATION_COMPLETENESS_FIELD_SPECS` in `file:src/contexts/question-theme/infrastructure/persistence/mongoose/constants/question-theme.mongoose.constants.ts`).

- Filters: the admin question and theme list endpoints accept `is-fully-translated` (`FULLY_TRANSLATED_QUERY_KEY = "is-fully-translated"` in `file:src/shared/application/dto/constants/translation-completeness-query.dto.constants.ts`) — `true` returns only complete resources, `false` only incomplete ones. Questions evaluate in **dynamic mode** against the document's own `applicableLocales` (falling back to all 6 locales when absent/empty), themes in **static mode** against all `LOCALES` (`buildIsFullyTranslatedMatchCondition` in `file:src/shared/infrastructure/persistence/mongoose/helpers/translation-completeness.mongoose.helpers.ts`, wired in `file:src/contexts/question/infrastructure/persistence/mongoose/repository/helpers/question-filter.mongoose.helpers.ts` and `file:src/contexts/question-theme/infrastructure/persistence/mongoose/repository/helpers/question-theme-filter.mongoose.helpers.ts`).
- Stats: question and theme stats report `byTranslationCompleteness { fullyTranslated, incomplete }` (`file:src/contexts/question/infrastructure/persistence/mongoose/repository/pipelines/question-stats/question-stats.mongoose.repository.pipeline.ts`, `file:src/contexts/question-theme/infrastructure/persistence/mongoose/repository/pipelines/question-theme-stats/question-theme-stats.mongoose.repository.pipeline.ts`).
- The public random-questions endpoint additionally requires that whatever fields exist be translated in the **requested locale** via the indexable single-locale variant `buildIsFullyTranslatedForLocaleMatchCondition` (`file:src/contexts/question/infrastructure/persistence/mongoose/repository/question.mongoose.repository.ts`).
- Completeness conditions are the database-level expression of the rule; there is no write-time enforcement — untranslated content is storable (that is what the filter surfaces).

## Applicable-locales policy

`Question.applicableLocales` (`file:src/contexts/question/domain/types/question.entities.ts`, schema prop in `file:src/contexts/question/infrastructure/persistence/mongoose/schemas/question.mongoose.schema.ts`) restricts a question to a subset of the 6 locales:

- Omitted or empty (`[]`) → all 6 locales apply; this default is baked into the completeness expression (`buildRequiredLocalesExpression`) and the public locale filter (`buildIsApplicableForLocaleMatchCondition`: locale matches when `applicableLocales` is absent, empty, or contains the requested locale — `file:src/contexts/question/infrastructure/persistence/mongoose/repository/helpers/question-filter.mongoose.helpers.ts`).
- Creation: `zQuestionApplicableLocales(1)` — optional, min 1, max `LOCALES.length = 6`, unique values (`file:src/contexts/question/application/dto/zod/validators/question.dto.zod.validators.ts`).
- Modification: `zQuestionApplicableLocales(0)` — an empty array clears the restriction and makes all locales applicable again (`file:src/contexts/question/application/dto/question-modification/question-modification.dto.shape.ts`).
- The public list/random endpoints filter questions by the requested locale using the rule above (`createPublicQuestionFilterOptionsFromQueryDto` in `file:src/contexts/question/application/mappers/question-filter-query-dto/question-filter-query-dto.mappers.ts`), so French-only questions never surface to other locales.

## translate-questions maintenance command

`.opencode/commands/translate-questions.md` (slash command `/translate-questions`) is the maintenance workflow for bringing all questions to full translation:

- Fetches not-fully-translated questions from the admin API (`GET /admin/questions?is-fully-translated=false&limit=100&sort-by=createdAt&sort-order=asc`) — `is-fully-translated=false` already accounts for `applicableLocales`.
- Processes questions **one at a time** with human approval at each step: display French source → identify missing locales → decide → translate or mark French-only → PATCH → verify.
- Translation case: French (`fr`) is the source of truth and is **never** included in PATCH payloads; target locales are `en`, `es`, `de`, `it`, `pt`. Missing mandatory fields (`statement`, `answer`) must be filled for all 5 target locales; optional fields (`context`, `trivia`) only when the French source is non-null. Translations go through `PATCH /admin/questions/:id` with a `content` payload (written to a temp file first).
- French-only case: `PATCH /admin/questions/:id` with `{ "applicableLocales": ["fr"] }` — used for lexicon questions, French-culture content, puns/wordplay where translation is not relevant.
- Translation is all-or-nothing (all 5 target locales or French-only; no per-locale exclusion), and every PATCH is verified by re-fetching the question and diffing French values against the pre-PATCH snapshot.
- The command ends with a summary and a lessons-learned retrospective; it never modifies itself without explicit user approval.
